# Game Construction And Backend Boundaries

`Game` is an abstract `ndlike.jax_like.JaxLikeImplementation` with a logical game batch `shape`, a `Players` object, and a coalition-to-value call contract. `Players` is also an abstract `JaxLikeImplementation`; each logical element is a player set. Its shape must broadcast to the game batch shape without enlarging it, allowing games to share player sets. Both base classes specify the array interface without choosing a backing representation; concrete classes supply the representation-specific hooks. Indexing selects games or player sets, while calling a game evaluates coalitions.

`Players[C]` owns coalition compatibility, and `Game[C, V].players` has type `Players[C]`. The general coalition alias leaves representation open; individual player types declare compatible representations through `C`. `Players.is_valid` returns a single boolean for the entire coalition batch, normally checking static type, dtype, and shape metadata rather than inspecting individual values. Games delegate this check with their batch shape, so a coalition must broadcast with the game batch even when the player sets are shared. Coalition-internal axes are interpreted by the player implementation and do not participate in logical batch broadcasting.

Model adapters construct games: a proposed `BaselineGame(model, background_data)` embeds a model using baseline imputation. Masking and linking may be implementation components, but no particular predictor/masker/link class hierarchy is required by the core API. Subsequent explanation steps are game transformations as specified in [ADR 0004](0004-everything-is-a-game.md).

Backend-specific conversion belongs at concrete adapter boundaries. Neither `Players` nor `Game` chooses a model backend. Transfers or data-sized conversions are construction/transformation work, not cheap game casts. Concrete backend adapters and their inference policies remain to be specified.
