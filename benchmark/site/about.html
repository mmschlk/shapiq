How the benchmark
works.

Shapley values assign credit to players working together. Computing them can be expensive. We compare estimators against exact answers across different kinds of games, at the same evaluation budgets.

01

First, define what a coalition is worth.

A game takes a subset of players—a coalition—and returns a payoff. A common recipe combines three ingredients.

  1. DatasetExamples to learn from

    Features, outcomes and a held-out example to explain.

  2. ModelA fitted predictor

    For example, a forest predicting an outcome from those features.

  3. ConstructionA coalition rule

    Keep selected features; replace missing ones using a specified background.

  4. Fixed gameSubset → payoff

    The resulting prediction is the coalition’s value, v(S).

For example

Adult Census + random forest + marginal feature removal. Fit a predictor, choose a held-out person, and average its predictions over background values for absent features. Players are features; the payoff is a class probability.

This is one recipe. Data valuation instead treats training examples as players and can use held-out model performance as the payoff.

Some games need no prediction model. Players can also be groups, ensemble members, image regions or text tokens. Throughout the benchmark, d means the number of players.

Exact answers are the expensive part.

A general d-player game has 2d coalitions. Evaluating them all gives a payoff table from which we can compute exact Shapley values and supported interaction indices.

General games

Enumerate once. Reuse the table.

The newer protocol restricts enumerated games to 11–20 players. We cache coalition payoffs so estimators can reuse the same game without repeatedly running the underlying model.

Structured games

Use a specialized exact solver.

Some tree, nearest-neighbor and product-kernel games have structure that permits exact computation at larger player counts. Each solver must support the specific game and explanation target, and match enumeration on small qualification cases.

Exact for which game? If game construction uses sampling, we freeze that realization. Ground truth is exact for its saved payoff table, not necessarily for the ideal expectation over infinitely many background samples. Earlier published snapshots may contain games below 11 players.

nMSE: how far is the estimate from the exact answer?

nMSE =sum of squared attribution errorssum of squared exact attributions

0Exact estimate

1Error of estimating every attribution as zero

> 1Worse than that zero estimate

Lower is better. Normalization makes differently scaled games comparable. We align the selected attribution coordinates and exclude the empty-coalition baseline. Zero-energy truth is unscorable; the newer protocol also excludes near-zero signals using its recorded scale-relative threshold.

Median nMSE

The default: a typical run under the benchmark’s balancing weights. It is less sensitive to occasional extreme errors. At exactly half the weight, we average the neighboring values.

Mean nMSE

The weighted average error. Rare, very bad estimates can move it substantially, making it useful for spotting instability that the median can hide.

Elo

How often an estimator achieves lower error on matched runs. We fit all paired outcomes together using a regularized Bradley–Terry model, centered at 1,000. Ties count as half wins.

Balanced summaries. Families receive equal weight, then settings within families, game instances, budgets and evaluation seeds within their groups. Successful partial results are reweighted over what is observed. Elo uses overlapping successful runs and fixed published presets; it describes relative wins, not the size of the error difference or universal quality.

Elo pairing and tie rules

We pair runs on the same game, explanation target, budget and evaluation seed. Errors within 1% of the larger nMSE plus 10−12 count as a tie. The batch fit uses an L2 penalty on its skill parameters; ratings are unavailable if the comparison pool is disconnected. There is no sequential match order.

Read coverage alongside the score.

Missing and failed runs never become zero error. Low-coverage methods can look good on an easier subset, so they appear below complete methods by default. Unsupported explanation types are separate from failures.

Check what “time” includes.

Cached runs measure estimator work and lookups. Estimated uncached time adds recorded, batch-amortized payoff costs; it is not a fresh end-to-end timing. CPU and GPU preparation have distinct hardware profiles.

History is a comparison today.

The historical plot places current benchmark scores at an estimator’s first verified publication date. It does not reconstruct past hardware, implementations or results; its curves use complete coverage.

05

Make every choice inspectable.

A ranking depends on the games we choose. Real data, richer models and exact answers help, but this collection cannot represent every application. We keep synthetic diagnostics separate and publish the ingredients, limits and provenance alongside the scores.
