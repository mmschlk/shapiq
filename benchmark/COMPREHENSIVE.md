# Comprehensive Shapley estimator benchmark

Approved 2026-10-06. This replaces the smaller plans in FOCUSED.md and ROADMAP.md.
The executable design is `suites/comprehensive.csv`, generated by
`shapiq_benchmark.comprehensive`. It is one benchmark, with preparation and
evaluation running together in a shared queue.

## Resources and execution

- At most **1,000 concurrent CPUs**, no production GPUs. This ceiling was
  reduced on October 7 to leave room for Hopper Monitor and other user jobs.
- **24,576 allocated CPU-hours total, including all prior campaign work**.
- The initial launch used sixteen allocations of 64 single-thread workers and
  512 GiB RAM for twenty hours each. One allocation was cancelled at the user's
  request on October 7; the remaining fifteen use 960 CPUs. Future allocations
  must fit the 1,000-CPU ceiling; release workers when work ends.
- Each game has at most two CPU-hours to prepare its exact reference. A timeout
  is an explicit resource exclusion, never an approximate reference.
- Existing jobs, frozen games, results, seeds and estimator settings stay intact.
  Reuse requires identical construction and authenticated artifacts.
- Byte-identical node-local dependencies are loaded before Python starts. Dataset
  downloads happen once, before parallel readers. No shared-environment installs.
- Atomic directory claims prevent cross-host duplicate work; a durable intent
  precedes each estimator execution. Interrupted attempts are not automatically
  retried. The ledger reserves allocation CPU-time before jobs are released.
- Automatic checks cover source identity, usable truth, duplicate prevention and
  resource limits. There are no per-batch human or independent approval gates.
  One consolidated coverage and score check precedes publication.

The CPU-hour cap is a ceiling, not a promise that every expensive combination
finishes. Publish actual coverage and explicit failures/exclusions; never hide
incomplete cells or infer completion from Slurm alone.

## Applications, player counts and ground truth

| Application | Players | Requested counts | Exact reference |
| --- | --- | --- | --- |
| Generic individual prediction | Input features | 4, 8, 12, 14, 16 | Evaluate every coalition of the frozen predictor/baseline game |
| Tree individual prediction | Input features | 8, 16, 32, 64, 128, 256, 512 | Matching path-dependent or interventional tree solver |
| Retraining data valuation | Groups of training rows | 4, 8, 12, 14, 16 | Refit and score every coalition of groups |
| Nearest-neighbor data valuation | Individual training examples | 32, 64, 128, 256, 512, 1,024 | Native exact KNN/TNN Shapley-value formulas; classification only |
| Feature selection | Input features | 4, 8, 12, 14, 16 | Refit and score every coalition of features |

Include the natural full input width below sixteen, and only feasible dimensions
and row counts. Never pad features or manufacture players. Feature subsets and
neighbor-row prefixes are nested within a construction seed. Group count and
model input width are separate axes in data valuation.

Exhaustive tables contain 16, 256, 4,096, 16,384 or 65,536 coalition values at
4, 8, 12, 14 or 16 players respectively. Existing direct derivative formulas avoid
dense exponential-by-exponential matrices above twelve players. Exact means exact
for the saved game, subject to documented floating-point error. Native solvers
must match the game's utility, masking convention and supported target. We do
not claim generic exact truth at hundreds of players.

## Models and controlled comparisons

Linear/logistic models and random forests provide a matched core across all 24
datasets and the three applications. Random forest, XGBoost and LightGBM supply
native tree games. At twelve players, XGBoost, LightGBM, SVM and MLP comparisons
use a fixed balanced subset: Adult, Breast Cancer, Digits, Bioresponse, Wine
Quality, Miami Housing, Superconductivity and QSAR-TID11.

The same subset has a separate input-width sweep at twelve valuation groups:
8, 16, 32, 64, 128 and the full width where feasible, using the core models.
No dataset or model is selected because its estimator scores look favorable.
Train/validation/test splits and model profiles are fixed and recorded.

The generated design contains 1,270 recipes and 5,080 intended instances before
resource and model-quality exclusions: 782 exhaustive recipes, 360 native tree
recipes and 128 native neighbor recipes. Four construction seeds are crossed
with three estimator seeds; design counts are not measured coverage.

## Estimators, budgets and scores

Retain the 22-estimator catalog and its explicit constructor settings. Evaluate
nine relative query budgets: **0.5, 1, 2, 4, 8, 16, 32, 64 and 128 times the player
count**. Requested budgets and actual queries are separate; small games can
saturate their entire coalition space. Unsupported method/target combinations
remain explicitly unsupported.

Use the existing target-aware coefficient-error metrics and weighting rules.
The three applications receive equal weight, followed by subtype and recipe
weighting. Datasets with more recipes can have more weight within an application;
the current hierarchy does not balance datasets separately. Zero-energy targets have no
normalized score. Failures have no invented timing or error value. Report success
coverage alongside scores, with construction seeds grouped for uncertainty.

## Publication

Keep the existing website dataset until the replacement is checked. Publish one
coherent cohort, its actual coverage, exclusions, frozen configurations and
reproduction artifacts. The About page is maintained as Markdown with a table
of contents. Preserve historical evidence on lab storage; remove obsolete active
paths only when they are no longer needed by a live job or reproduction record.

If admitted allocations end before all work is attempted, an authenticated
closeout records that fact separately from execution completeness. The public
coverage inventory includes unprepared instances and unattempted cells; neither
receives an invented reference or score. Ending allocations does not by itself
establish that the global CPU-hour cap was exhausted.
